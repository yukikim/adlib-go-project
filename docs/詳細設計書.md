## 5. フロントエンド構成詳細

### 5.1 ポータル構成

- `PortalWorkspace` を member / admin / auth の共通 shell とする
- 描画は以下の component に分割する
  - `AuthPortalSection`
  - `MemberPortalSection`
  - `AdminPortalSection`

### 5.2 状態管理方針

- 認証フォームと認証 action は `useAuthPortal` に集約する
- メンバー向けプロフィール、SessionEntry、レイティング状態は `useMemberPortal` に集約する
- 管理者向け SessionEvent、sessionSet、アーカイブ、お知らせ、コラム状態は `useAdminPortal` に集約する
- `PortalWorkspace` は shared data の取得と section component への受け渡しに責務を絞る

## 4. 認証・認可詳細設計

### 4.1 認証方式

- メールアドレス + パスワード認証
- セッションベースまたは JWT ベースを採用候補とする
- パスワードはハッシュ化して保存する

### 4.2 認可方式

- role によりアクセス可否を制御する
  - guest
  - member
  - admin

### 4.3 パスワード再設定

- 再設定トークンを発行する
- メールリンク経由で再設定画面へ遷移させる
- トークンには有効期限を持たせる

## 5. sessionSet 詳細設計

### 5.1 入力データ

- SessionEvent
- SessionEntry
- Participant
- ParticipantSongRequest

### 5.2 通常生成詳細

- round1 の曲を候補曲とする
- drum / bass / piano は必須とする
- 希望者を優先する
- 上限に達した参加者は候補から除外する
- vocal 参加時は front を 1 名までに制御する

### 5.3 sessionSetForce 詳細

- 未生成曲のうち希望者不足のみ対象とする
- requesterCount の多い順で処理する
- 不足必須パートは以下で選ぶ
  - 参加上限未満
  - 参加曲数が最少
  - 同率ならランダム

### 5.4 出力データ

- sessionSets
- forcedSessionSets
- skippedSongs

### 5.5 レイティング詳細

- レイティング対象は公開済み sessionSet とする
- 1 メンバーが 1 セットに対して 1 件評価できる想定とする
- レイティング値は星 1 から 5 の整数とする
- 再評価可否は今後の要件詳細化で確定する
- 管理者向けには平均、件数、分布を集計して返す

### 5.6 アーカイブ詳細

- アーカイブには以下を保存する
  - セッション実施日
  - 場所
  - 参加人数
  - 参加者リスト
  - sessionSet スナップショット
  - 各セットのレイティング集計結果
- sessionSet 編集前でも編集後でも保存可能とする
- 複数版の保存を許容する設計とする
  - 管理者は任意のタイミングでアーカイブを削除できる
